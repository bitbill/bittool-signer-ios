# BitTool Signer 1.0.0: public protocols, export semantics and compatibility acceptance

The 21 September 2026 modification specification is the Revision 1 baseline. Revision 3 (22 September 2026) changed several of its decisions at the user's request: Bitcoin now exports an Account XPUB by default and the leaf-public-key mode is gone; TRON can export any address index, no longer limited to 0–99; and the supported-wallet list dropped Ownbit, listing only wallets with first-party evidence. What follows is updated to Revision 3. It distinguishes throughout between verification against code or reference SDKs and real-device pairing, requests and scanned-back responses with a specific hot wallet version. **A reference library being able to parse something is not the same as a wallet in the App Store having completed three-stage interoperability.** There is currently no complete hot-wallet round-trip matrix that could be presented as certified.

## Public transport scope

| Chain | Pairing export | Signing request → response | Limits |
|---|---|---|---|
| BTC | `crypto-account`: single-sig account XPUB (default) or address only; multisig cosigner XPUB | `crypto-psbt` → `crypto-psbt`; `ur:psbt` → `ur:psbt` | Existing public BBQR H/2/Z and PSBT hex/base64 file compatibility is retained, including multi-line wrapped base64; the response uses the same UR type as the request; no product-specific format tab is added |
| EVM | `crypto-hdkey` account node; can switch to address only | `eth-sign-request` → `eth-signature` | dataType 1/2/3/4; the specific signature type, network and risk are checked by the chain parser |
| SOL | `crypto-multi-accounts`, carrying only the current preset; can switch to address only | `sol-sign-request` → `sol-signature` | Transaction and Message are separate; returns a 64-byte detached Ed25519 signature |
| TRON | The current index as a plain address (`m/44'/195'/0'/0/i`, i = 0 … 2³¹−1) | `tron-sign-request` → `tron-signature` | Checked against the public Keystone SDK fields and fixed wire samples; a September 2026 survey found no mainstream hot wallet that generates this request from a plain-address export (see below) |

TokenPocket's `scheme:action-version=...&protocol=TokenPocket...`, TP dynamic sharding, the old `keystone-sign-request`, and external `bittool-signer-json` signing requests and responses have all been removed or are refused. The internal Swift↔JS JSON dispatch is an in-process interface only. PSBT files can still be imported, and the plain-address, recovery-phrase and transaction-signing entry points stay separate.

## Recovery phrase languages and backup formats

- **Import**: all 10 official BIP39 wordlists — English, 简体中文, 繁體中文, 日本語, 한국어, Español, Français, Italiano, Čeština, Português. The wordlists are taken byte for byte from bitcoin/bips with pinned SHA-256 hashes, and were checked word by word against two independent sources, @scure/bip39 and ethers. The seed is computed per BIP39 from NFKD-normalized words, consistent with other standard wallets, and verified against @scure/bip39 reference vectors and the official bip32JP Japanese vectors, including a passphrase with compatibility characters.
- **Tolerance**: accents may be omitted, capitals are accepted, numbering and commas are allowed; Chinese may be entered without spaces and Japanese with full-width spaces. The app always converts back to the official spelling before computing a seed. If the same unaccented words are valid in two languages — Italian "nomina solido comodo …" is also valid Spanish once accented — those are different wallets, and the app asks which language was used.
- **QR import**: Standard SeedQR defines the English wordlist only. A QR code containing the words themselves, such as the app's own phrase QR, works for every language and is imported with the exact spelling in the code, without asking.
- **Creation**: new wallets still generate an English phrase, for the widest compatibility.
- **Phrase QR**: the QR tab on the backup page shows a plaintext phrase QR — words separated by spaces, without the BIP39 passphrase — for moving a wallet to another device of your own in private. Any wallet that can import a phrase by QR can read it. Concealed by default, revealed on a tap, with no save or share. The previous encrypted backup format (`BSBK1:`) has been removed.
- **Recovery cards (2 of 3)**: three cards, each hiding a third of the words, so any two reconstruct the phrase. The layout depends only on the word count — three positions per row, one hidden per row, staggered row by row — so it is identical when reopened or generated on another device. At 24 words a single card is missing 8 words, about 80 bits; at 12 words only 4, about 40 bits, which is brute-forceable, so 12 and 15 words show a warning.

## Exact differences between pairing outputs

The Bitcoin single-sig profile order is `native`, `taproot`, `nested`, `legacy`, for accounts `m/84'/0'/0'`, `m/86'/0'/0'`, `m/49'/0'/0'` and `m/44'/0'/0'`.

| BTC mode | What it actually contains | Can public derivation continue? |
|---|---|---|
| `accountXpub` (default) | The account node's public key, chain code, origin, parent fingerprint and script expression | Yes: `/0/i` and `/1/i` |
| `address` | The full receiving address text for `/0/0` | No |

The previous `publicKey` mode — the `/0/0` leaf public key with no chain code — has been removed. BCR-2020-015 specifies that `crypto-account` carries account-level HD public keys only, and the parsing code of every wallet surveyed in September 2026 (Sparrow, BlueWallet, Nunchuk, Specter, Keeper, ZEUS and others) requires a chain code; none could import that format. The engine now refuses the mode.

Taproot uses the standard tag **409** for the BCR output expression `tr`, exports the internal key untweaked, and applies the BIP86 tweak for addresses. An independent CBOR decoder checks the output after registering that published standard tag, and the result is also verified against the internal key and address vectors published with BIP86. Taproot is never disguised as `wpkh`.

BTC `multisig-native` and `multisig-nested` export the `m/48'/0'/0'/2'` and `m/48'/0'/0'/1'` account XPUBs with `wsh` and `sh(wsh)` cosigner context. That container holds one participant only — **no threshold, no other participants, no final receiving address and no complete policy** — and takes no part in generating on-chain scripts. The actual public keys differ between script paths.

EVM Wallet exports the `crypto-hdkey` for `m/44'/60'/0'` with children `0/*`; Address is fixed at index 0. The address browser can still page through multiple indices.

SOL Standard, Trust and Legacy are `m/44'/501'/0'/0'`, `m/44'/501'/0'` and `m/44'/501'` respectively. All three public keys are cached locally; Coin Level exports only the current one, and no Solana XPUB is offered. These are exactly the three path shapes Keystone provides to Solflare and Helium (account-based, single account, sub-account). Matching recovery paths is not in itself QR signing certification.

TRON exports only the current `m/44'/195'/0'/0/i` address, where `i` is any non-hardened index from 0 to 2³¹−1, set by stepper or typed directly. The account node and an address cache for indices 0–99 are stored locally; other indices are derived from the account node on demand. No invented wallet format is shown where there is no verified public pairing payload.

Every address mode encodes the address text and nothing else: no URI scheme, JSON, UR prefix, amount, UUID or path. The copied text equals what the QR code actually contains, and an animated export is the newline-joined text of every displayed frame.
## Wallet-level pairing (bittool-signer-wallet v1)

The Pair page offers **Wallet Level** alongside Coin Level, which it still opens on by default; the Pair group on a wallet's detail page links straight to it. One **animated multi-frame** QR code (`ur:bytes`, 400-byte fragments) carries watch-only information for all four chains, so a multi-chain wallet that has implemented BitTool Signer wallet-level pairing can import everything at once.

The payload carries **seven accounts**: account-level xpubs for four Bitcoin script types (`p2wpkh`, `p2tr`, `p2sh-p2wpkh`, `p2pkh`), an EVM xpub, a TRON xpub, and **three Solana addresses** (standard, trust, legacy). Ed25519 derivation is hardened, so there is no Solana xpub and a watch-only wallet cannot derive one address from another — all three are sent. The two `m/48'` multisig profiles are not included: multisig needs every cosigner's public key and the threshold, which is what the Coin Level cosigner export is for. The payload is 1,561 bytes of inner CBOR across 4 frames, so it does not fit in a single QR code and **a receiver must collect every frame before decoding**.

`mode` is `full`, as the draft defines it, and does not appear in the interface as a Simple/Full choice. The format follows the draft the user supplied: `ur:bytes` carrying canonical CBOR (RFC 8949 §4.2.1), with field names identical to the JSON keys. A `masterFingerprint` field is added — v1 parsers ignore unknown fields — so a watch-only wallet can put the correct fingerprint in PSBTs and signing requests. The exact encoding, test vectors and security notes are in [docs/Wallet-Pairing-v1.md](Wallet-Pairing-v1.md).

The wallet supported by default is **BitTool Wallet** (BITTOOL PTE. LTD., iOS and Android; [App Store 6761503126](https://apps.apple.com/app/id6761503126), linked from bittool.com; listed at the publisher’s direction). Sparrow, MetaMask and the rest continue to use the chain-specific Coin Level formats.

> **Receivers must be updated for this shape.** The `accounts` array went from 4 entries to 7, entries must be read by their `chain` and `script` or `profile` fields rather than by index, Solana entries carry a `profile` field, and all frames must be collected before decoding.

Only "confirmed" entries are kept; anything "unclear" is omitted. ## The QR payload view

Under every Coin Level QR code, the Wallet Level QR code and the signature result QR code there is a collapsed **Payload** section that can be opened to see what that QR code actually carries, with a "Copy Payload" action that writes only to the local, expiring clipboard and never goes through Handoff. For Coin Level and signature results the content comes from the engine **re-decoding the frames it has just generated** (`describeQR` in `engine/protocols.js`), not from reassembling the generator's inputs, so it matches the QR code byte for byte; if a frame cannot be decoded back as its own type, that is an error and no QR code is shown. Wallet Level shows the object that was canonically CBOR-encoded (in v1 the CBOR text keys are the JSON key names; the encoding rules and vectors are in [Wallet-Pairing-v1.md](Wallet-Pairing-v1.md)).

- **Format**: a UR map shows as "Payload (JSON)"; a UR holding a single byte string shows as "Payload (Hex)"; a plain-text QR code, which only address exports produce, shows as "Payload (Text)" with the QR text itself. The card's "Format" line gives the transport and the byte count, for example `ur:crypto-account · CBOR · 162 bytes` or `Plain text · 34 bytes` — the byte count being the length of the CBOR inside the UR, or of the PSBT itself.
- **Naming**: integer keys are shown by their registry field names (crypto-hdkey, crypto-keypath and crypto-coin-info per BCR-2020-007, crypto-account per BCR-2020-015, and crypto-multi-accounts and the eth-, sol- and tron-signature types per the Keystone registry); a tagged value shows as a single-key object keyed by the tag name (303 crypto-hdkey, 304 crypto-keypath, 37 uuid; output descriptors 400–410 use the CDDL names from BCR-2020-010, such as `witness-public-key-hash`, `script-hash` and `taproot`); byte strings are lowercase hex. JSON is displayed sorted by key, since a CBOR map is itself unordered.
- **Divergence from the specification is shown honestly**: BitTool Signer's crypto-account follows the Keystone and Sparrow convention, with **no** BCR-2020-015 `#6.308(crypto-output)` wrapper around the output descriptor. The view shows the actual encoding.
- **Fingerprints**: master, source and parent fingerprints in a UR are 32-bit integers per the specification, so JSON shows them in decimal (1942346250 for the test phrase); the Payload section notes that this is the same fingerprint shown in the interface (1942346250 = 73C5DA0A). Wallet cards, the detail page, the review page and Activity all show this master fingerprint — what used to be called "Wallet ID" is now "Fingerprint" — and it is the same value as `masterFingerprint` in the Wallet Level payload. Internal identity and signature matching still use `walletKeyId`; the fingerprint is for display only.
- **Signature results**: eth-, sol- and tron-signature show `request-id` (as `{"uuid": …}`) and `signature`. Every Bitcoin PSBT return form — crypto-psbt, psbt, BBQr, base64 and hex text — is reassembled by the same collector that reads requests, and shows `psbt_base64` (the complete PSBT the QR code carries) and `decoded` (reference information parsed from it, using Bitcoin Core `decodepsbt` field names, with amounts as integer `value_sat` and the txid of the unsigned transaction; sorted by key so it stays visible even when a large PSBT is truncated for display). Beyond 30,000 characters the interface lays out only the first 30,000; copying still yields the whole thing.
- The signature result page keeps a single primary button, **Done**; "Export as File" moved inside the Payload card as a secondary action.

## Encoding and raw bytes

- Bytewords and fountain encoding from bc-ur 1.1.13, with recovery from out-of-order, repeated and mixed fountain frames. The type, count, checksum, message length and fragment length must all belong to the same group.
- BBQR validates the base36 index, the encoding and the fragment length; Z uses fflate's bounded streaming raw-DEFLATE decompression. That protocol has no global session ID, so a complete PSBT must still be reviewed.
- An ETH request ID, where present, is accepted as **1–64 raw bytes** under tag 37. Real imToken requests have used a 36-byte opaque correlation ID; it is not converted to UTF-8, truncated or regenerated. SOL and TRON currently keep the 16-byte UUID boundary. Wrong tags, wrong types, and empty or oversized values are refused.
- ETH signature encoding: legacy transactions return an EIP-155 `v` without truncating large chain IDs, typed transactions (2930/1559) return y-parity, and messages and EIP-712 return 27/28. SOL is always 64 bytes; TRON is always 65 bytes of `r || s || recovery`, with recovery 0 or 1 in the public SDK samples.
- `tron-sign-request` CBOR fields: 1 request ID, 2 signData bytes, 3 dataType, 4 derivation keypath, 5 optional address bytes, 6 origin. dataType 1 is the raw `raw_data` protobuf; 2 is a personal message. The optional address is currently validated as a 21-byte binary TRON address whose first byte is 0x41. Without an address, the public index matching rules still have to be satisfied.
- The public TRON response is a detached signature; the hot side keeps and aggregates other members' signatures. Internal transaction signing verifies and preserves the signatures already in a request, and does not treat the operated account, new permission members or owner fields as the signer.
- The original CBOR and PSBT bytes stay in the normalized request's transport, and are re-verified against the structure to be signed before signing. `origin` is unauthenticated display information only.
- Foreseeable protocol refusals return controlled `QR_PROTOCOL` text; unknown type names, input key names and third-party exceptions are never echoed verbatim into an error message.

A local reproduction of the imToken problem of 21 September 2026 confirmed it: a real single-frame `eth-sign-request` carried a 36-byte ID that an older version wrongly limited to 16. The fixed bundle parsed and reviewed the real QR code successfully. **That real transaction was neither signed nor broadcast**, and its actual content never entered the repository or any online lookup. None of this amounts to imToken having passed scan-back signing acceptance.

## Public index, parsing and authorization interfaces

The complete interface is in [engine/README.md](../engine/README.md). The product calls it in this order:

```text
derivePublicIndex (authorized briefly, once, on create / import / repair; the host computes the
                   BIP39 seed with native PBKDF2-HMAC-SHA512 and passes it in)
  → public cache only: derivePublicAddresses / createPublicPairing
  → decodeQR / decodePayload
  → review + resolveSigningPlan (entirely from local public wallet records)
  → the password for the wallet named by each fixed task
  → signPlanTask (validates the plan, re-derives and checks the real public key)
  → encodeResponse (the original request's public profile)
```

Each wallet stores six Bitcoin nodes, one EVM node, one TRON node with 100 addresses, and the three Solana preset public keys (public index version 1). The stable `walletKeyId` is a version-domain-separated SHA-256 binding the master public key material of a valid seed; no master XPUB is emitted, and a short fingerprint is never used in place of identity.

EVM falls back to index 0 only when a path is missing; SOL has exactly three presets; a TRON request carrying a path — which `tron-sign-request` always does — can match any index, while a request with an address but no path is compared only against the cached indices 0–99; Bitcoin without derivation data tries only each registered single-sig `/0/0`, and a cosigner additionally requires an explicit public key match in the script. A valid request with a path can match Bitcoin receive and change addresses and non-zero EVM indices. Having viewed an address does not widen the fallback range.

Nothing is signable when there is no match, when information is missing, when the result is ambiguous, when the cache is incomplete, or when the structure is invalid; there is no manual selection and no trial decryption across the whole store. One PSBT can produce several fixed wallet tasks, each authorized by its own password. An accumulating PSBT must leave the global, input and output metadata and the original transaction unchanged, adding only signatures.

## Chain parsing and signing boundaries

- **BTC**: PSBT v0 and v2; the four single-sig types; P2SH, P2SH-P2WSH and P2WSH multisig; Taproot key-path and c0 CHECKSIGADD/CHECKSIGVERIFY threshold leaves. Only ALL and DEFAULT sighashes are accepted; legacy and SegWit v0 need the complete previous transaction, while all-Taproot can use witness UTXOs. MuSig2 and arbitrary unknown scripts are not supported.
- **EVM**: legacy, 2930 and 1559 transactions; personal messages of arbitrary bytes; EIP-712, where values must match their declared types strictly — truthy strings posing as bools are refused, as are ambiguous integer and address spellings — and the separator is computed in the declared `EIP712Domain` order, ignoring unused types. Safe gas refunds, native currency sent with a call, fees, and transfers of tokens outside the registry are shown in the review and raise the risk level. Safe CALL and DELEGATECALL, MultiSend, permission changes and canonical Permit and Permit2 are parsed. Unknown calls and deployments are marked opaque and custom typed data partially decoded, with risk confirmed per request; unknown content is never presented as decoded. The mainnet table covers chains 1, 56, 42161, 8453, 10, 137, 100 and 43114, and the token registry now covers all eight EVM mainnets plus TRON and Solana. Blobs, 7702, raw-hash `eth_sign` and unknown networks are refused.
- **SOL**: legacy and v0 static keys with the correct required signer slots; System, the common SPL instructions, ATA, compute, memo and stake. Token-2022 extensions and Squads proposal references are partially parsed, unknown programs are opaque, and address lookup tables are still refused. Message is a separate type accepting only 1–1024 bytes of recognizable UTF-8 text, including Chinese, and refusing a transaction header prefix; a transaction that cannot be parsed is never downgraded to a message. Durable nonce transactions are flagged, and a summary never joins one transfer's amount to another's recipient.
- **TRON**: TRX, the common token and NFT ABIs, permission updates, Stake 2.0 and resource types 54–59, and official length-prefixed personal messages — a non-text message shows its raw bytes, is marked opaque and must be confirmed each time. Call value and a high fee limit are shown. Unknown protobuf and contract types and TRC10 are refused. Current permission members, balances and the network it will eventually be broadcast to cannot be confirmed offline.

### How NFTs are shown in the review (Revision 3)

An offline signer cannot obtain an NFT's name, image or floor price, so it shows only what the request bytes prove, and says plainly when something cannot be determined. Review cards use dedicated icons for NFTs (NFT, ERC-1155, "NFT or token" with an orange question mark, marketplace order), show "NFT contract (not verified)", "Mint" or "Asset ID" with the full address under the headline, and abbreviate an over-long token ID in the headline (first 8 and last 8 digits with the digit count) while showing it complete in the card.

- **EVM and TRON contract calls**: `safeTransferFrom` (ERC-721) shows "Send NFT · NFT #id"; a single ERC-1155 transfer shows "quantity × #id", and a batch is merged into one "Items" field that flags repeated IDs and zero quantities. `setApprovalForAll(true)` is a red HIGH RISK explaining that the operator can move every token this account holds in that contract, including ones received later, while revoking is yellow. `approve` and `transferFrom` on a contract absent from the token registry are shown as "NFT or token" with both readings; `approve(X, 0)` is no longer mislabelled "Revoke", and `approve(0x0, id)` shows as "Clear NFT Approval (if ERC-721)". A MultiSend headline lists its sub-calls, and sub-warnings are prefixed "Call k:" and deduplicated. ENS `.eth` names, on Ethereum mainnet only, add an explanatory field without guessing at a name. TRON's TRC-721 is handled the same way, with addresses shown in Base58.
- **NFT marketplace signatures (EIP-712)**: Seaport 1.5 and 1.6 including BulkOrder, LooksRare v2 Maker and BatchOrder, and Blur are identified by exact type string and (name, version, verifyingContract). Seaport and LooksRare show "you give / you receive / someone else receives", with red warnings when: you receive nothing; a Dutch auction price falls to 0; most of the payment goes to someone else; the buyer may choose any token in your contract (criteria 0); the order effectively never expires; the order's signer is not the signing wallet; an item marked as an NFT is in fact an ERC-20 from the token registry (so "NFT #5e18" would really move 5 WETH); or the shape is Seaport's but the contract is unrecognized. Blur's Root and V2 sign only a Merkle root, whose contents are invisible, so they are always marked undecoded with a red warning — as is any other typed data that signs a single bytes32 or whose type name contains root, tree or merkle. OpenSea fee addresses, conduits and zone labels appear as explanatory text only on chains where they have been verified, and never lower the risk level. Only for these recognized marketplace requests are undeclared message fields ignored — they take no part in the signature, are not displayed, and produce a count warning; all other typed data still refuses extra fields.
- **Solana**: an SPL or Token-2022 transfer of 1 unit of a 0-decimal mint absent from the registry shows as "Send Token (likely NFT)", because ordinary 0-decimal tokens match that pattern too. When the same transaction contains a matching ATA creation instruction and no undecoded instructions, the recipient is shown as a wallet address; otherwise the token account is shown with a caution. Metaplex Token Metadata TransferV1 is marked as an NFT only when the edition PDA for that mint is supplied, and the metadata, edition and token record PDAs are all validated. Bubblegum compressed NFTs (`transfer` and `transfer_v2`) validate the tree config PDA and derive the asset ID from the tree and nonce. Metaplex Core TransferV1 accepts only the exact `[14,0]` data. Delegate signatures, rule sets and transfer hooks each carry a warning — for a hook, all that can be said is "the transaction supplies accounts for hook X", since the mint's actual hook cannot be confirmed offline. Marketplace programs such as Magic Eden, Tensor and Auction House show their name only, marked undecoded and high risk. Token Metadata Delegate, Revoke, Lock, Unlock and Burn describe exactly what the delegate can do for that role — StandardV1, for instance, can transfer, burn and freeze. When every substantive instruction is undecoded, the whole transaction is marked "Not decoded".

No NFT display uses a green "verified" indicator. Every constant — selector, type string, contract address, program ID, discriminator and account order — was checked against official repositories and reviewed independently. The tests are `engine/test/nft-evm.test.mjs`, `engine/test/nft-solana.test.mjs` and `BitToolSignerTests/NFTReviewDisplayTests.swift`.

An invalid structure, an unsupported signature algorithm, or missing trustworthy key-location evidence cannot be bypassed by acknowledging risk. Static token metadata is for display and proves nothing about contract behaviour.

## Limits and test evidence

Up to 2,048 frames are accepted (1,295 for BBQR), 4,300 characters per frame, 1 MiB of accumulated text and a 128 KiB decoded payload. CBOR depth 24 and 20,000 nodes; JSON depth 32 and 20,000 nodes. Repeated keys, imprecise integers, indefinite-length CBOR, wildcard signing paths, unknown signature types and recognizably mixed sessions are all refused. A QR checksum is not identity authentication.

The full engine suite passes **210/210** with no failures, skips or cancellations. Alongside the existing protocol, public index, resolver and chain coverage tests and `test/hardening.test.mjs` (every engine issue from the Revision 2 internal review, Bitcoin change re-derivation, and seed and phrase input consistency), the suite includes `test/wallet-pairing.test.mjs` (wallet-level pairing), `test/nft-evm.test.mjs` and `test/nft-solana.test.mjs` (NFT display), `test/pairing-payload.test.mjs` and `test/response-payload.test.mjs` (the QR payload view: 22 Pair exports and 17 signature returns, with UR exports, eth and sol signatures and crypto-psbt cross-checked item by item against Keystone's parser, and addresses, BBQr, PSBT text and tron-signature checked with independent decoders), `test/bitcoin-fee-warning.test.mjs` (the fee policy), and `test/audit-bts-2026-1018.test.mjs` and `test/audit-bts-2026-1018-r2.test.mjs` (the two rounds of review findings). The token registry test checks all 3,350 records item by item: address shape, identity uniqueness, decimals as read on-chain, the source fields of each of the two layers, Solana's token program binding, and that the icon pack has no holes and every image's byte hash equals its id.

The current bundle is **1,181,026 bytes**, SHA-256 `6933d0d8a6f60faa8222506ac0bd7eef80eb884c9f73e31e9f354b4740f21077`; see [bundle-manifest.json](../engine/bundle-manifest.json). Public host vectors are in [public-plan-vectors.json](../engine/test/fixtures/public-plan-vectors.json). Native JavaScriptCore, UI and real-device camera results are in the implementation status; Node tests do not stand in for them.

Before release, every QR signing record must contain: the wallet, platform and version; the chain, path and output mode; the pairing payload; the request method and a sample; the response; independent signature verification; and a real camera scan round trip. Any route without hot-side real-device evidence stays unverified.
