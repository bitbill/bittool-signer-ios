# BitTool Signer v1.0.0 security design

> Revision 2 (2026-09-21 overhaul). The app has not shipped, so this revision uses new storage formats (vault v2, authenticated public files) without migration of earlier development data.

BitTool Signer is an offline software signer for iOS. It keeps key derivation and transaction signing on the device. It is not a hardware wallet, does not make an iPhone air-gapped, and has not received an independent security audit. The release version number is not a security certification.

## Recovery phrase storage

A vault contains a BIP39 recovery phrase in one of the ten official wordlists (new wallets are generated in English; imports keep their language, stored as the canonical NFC words) and, when configured, its separate BIP39 passphrase. The wallet password protects the local vault; it is not the BIP39 passphrase and does not change blockchain addresses.

Each wallet is stored separately in the application's private `Library/Application Support/BitToolSigner/Vaults/<UUID>.bsvault` directory:

1. Generate a fresh 32-byte salt with Apple's `SecRandomCopyBytes`.
2. Derive a 256-bit password key using CommonCrypto PBKDF2-HMAC-SHA256 with 600,000 iterations.
3. Encrypt the secret JSON using CryptoKit AES-256-GCM with a fresh automatically generated 96-bit nonce and a 128-bit authentication tag.
4. Encrypt that combined ciphertext again with an independent random 256-bit device key, also using AES-GCM with a fresh nonce.
5. Store the device key in Keychain with `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` and synchronization disabled. Creating a vault fails if device passcode protection is unavailable. There is no weaker production fallback. A separate DEBUG + Simulator-only UI test harness uses an isolated temporary directory and public test vectors; this code is excluded from all device and Release builds.
6. Save the outer ciphertext using complete file protection, owner-only filesystem permissions, backup exclusion, and a staged atomic rename. Protection and backup attributes are applied before replacement so preparation failures leave the previous password valid.

The file header contains the format version (2), KDF parameters, salt, wallet ID, wallet name, and creation time in milliseconds. These fields are not secret. The vault stores the header as the exact bytes that were authenticated, and each AES-GCM layer uses a domain-separated associated data string (`com.bittool.signer.vault.v2/<layer>` followed by those bytes). Re-encoding, reordering, or editing any header byte therefore fails authentication; the parser never re-serializes the header before checking it. Renaming changes the authenticated public display name without changing the encrypted header or key identity; it is a label, never proof of signer ownership. The recovery phrase, BIP39 passphrase, wallet password, and derived private keys are never written to plaintext files by the application.

Passwords and the device key are both needed. The encrypted vault file is deliberately not a portable backup. Device loss, application deletion, or removing the device passcode can make it inaccessible. The written recovery phrase and the separately recorded BIP39 passphrase are the recovery mechanism.

The device key is an OS-protected Keychain item. BitTool Signer does not claim that this symmetric key lives inside the Secure Enclave or that blockchain signatures are produced there.

## Why PBKDF2 in this version

Argon2id is a strong choice for password-derived encryption because its memory cost raises the cost of parallel password guessing. A future Argon2id migration should use a pinned, reviewed native implementation, a versioned vault format, published test vectors, and measured performance on the oldest supported device.

This version uses CommonCrypto's existing PBKDF2 implementation and CryptoKit's authenticated encryption to avoid introducing another native cryptographic dependency during the initial implementation. Its 600,000-iteration PBKDF2-HMAC-SHA256 cost follows the current OWASP PBKDF2 guidance. This is a documented implementation choice, not a claim that PBKDF2 offers Argon2id's memory hardness, or that this application is FIPS certified.

Passwords contain 8–64 characters and at least three of uppercase letters, lowercase letters, numbers, and symbols. Control characters are rejected. Passwords are used exactly as entered, without trimming or Unicode normalization. Long passwords remain available rather than imposing a 20-character cap. Meeting the composition rule does not make a predictable password strong; use a unique, long password.

Relevant references:

- [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- [Apple: Restricting Keychain item accessibility](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility)
- [Apple: kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly](https://developer.apple.com/documentation/security/ksecattraccessiblewhenpasscodesetthisdeviceonly)

## Authentication and local retry delay

There is no global active wallet, account unlock session or cached signing password. Public addresses, pairing and activity are accessible without opening a seed, subject only to optional App Lock. Backup display, password changes, deletion and every signing task authenticate the specified wallet separately.

A public-only, versioned index is stored in `Library/Application Support/BitToolSigner/PublicWallets/<UUID>.json`, with complete file protection, owner-only permissions, backup exclusion and atomic replacement. It contains six BTC account nodes, EVM/TRON account nodes, 100 cached TRON addresses (indexes 0–99, used only to match requests that carry an address but no derivation path; any other TRON index is derived from the TRON account node when browsing, exporting or matching a request with a path), three concrete Solana preset public keys and the display name. The index format is version 1. Wallet-level pairing exports only public data from this index: the BTC BIP84, EVM and TRON account xpubs and the standard Solana preset address `m/44'/501'/0'/0'`. It contains no mnemonic, seed, passphrase or private key. `walletKeyId` is SHA256 of the versioned domain plus master compressed public key and chain code. It is distinct from the local UUID and the short BIP32 fingerprint. The interface labels each wallet with its master fingerprint (the same value pairing QR codes export), for display only; `walletKeyId` stays the internal identity, and fingerprint matches alone never authorize signing.

Each public file is an envelope (`schemaVersion` 2) holding the Base64 body and an HMAC-SHA256 over a domain label, the wallet UUID and the body. The HMAC key is a random 256-bit app key kept in the Keychain with the same `WhenPasscodeSetThisDeviceOnly` protection as device keys. A file that fails verification, belongs to another wallet UUID, or exists without the key is treated as missing: the wallet shows **Repair Wallet Data**, and one password entry rebuilds it. Someone who can write to the app container therefore cannot substitute the public keys, addresses or names that drive matching and review.

Missing or invalid public indexes require a repair for that wallet only; repairing never regenerates keys or decrypts other wallets. Duplicates among ready indexes are rejected on import. A duplicate that still appears (for example after a repair) is retained, marked ambiguous and cannot be chosen arbitrarily to sign. New creation derives and saves the index before publishing the wallet card; failed persistence rolls back newly created data.

The resolver checks request paths, fingerprints, public keys, addresses, scripts and signer slots for consistency. It produces an immutable plan binding the request digest to specific wallet identities, paths and input/slot assignments. No user-selected fallback wallet or whole-library seed search exists. Missing signer information, missing public setup, no match and ambiguous matches are separate failures. After password authentication the engine re-derives and rechecks the actual keys before signing, then verifies produced signatures. Multiple local Bitcoin cosigners have separate tasks and separate password authorizations.

App Lock defaults off. Enabling it requires successful Face ID and at least one saved wallet. It protects app access only, never signing. Enabled cold launches start locked. A background interval of 120 seconds or longer requires new authentication; shorter intervals preserve app access. The interval uses `CLOCK_MONOTONIC_RAW`, which keeps counting while the device sleeps and ignores wall-clock changes. (`systemUptime` pauses during sleep, which would have let a phone that slept for hours reopen without authentication.) There is no foreground idle timer. Face ID's temporary inactive phase does not count as a background transition. Retry and any saved wallet's password are available; password fallback returns no secret or signing authorization. Removing the last wallet disables App Lock. A failed wallet-list load is not treated as an empty list.

Password failures are recorded per wallet in a separate authenticated, encrypted `.attempts` file using the device key, complete file protection, backup exclusion, and atomic replacement. The attempted counter is persisted before password derivation, so terminating or relaunching the application does not reset it. After five unsuccessful attempts, delays grow exponentially from two seconds to a maximum of five minutes. Successful authentication resets the count. The application never destroys a wallet in response to failed passwords.

This delay is an application control, not a secure hardware counter. An attacker who can modify or roll back the application's filesystem, control the device clock, extract the Keychain key, or run code in the process can interfere with it. The KDF and authenticated encryption provide the underlying cryptographic protection. iOS process isolation, device passcode strength, and OS integrity remain part of the threat model.

## JavaScript signing boundary

Native Swift code owns random-number generation, vault encryption, Keychain access, lifecycle controls, and the UI. JavaScript handles chain formats, derivation, transaction inspection, and signatures through the locally bundled `signer.js`.

- The bridge uses JavaScriptCore, not a web view. It exposes no network, DOM, filesystem, or wallet-storage interfaces.
- Operations run on a serialized actor under a fixed allowlist. Release builds accept only the production operations; test utilities (for example raw single-key signing or QR encoding) exist only in DEBUG builds.
- Any operation that receives secrets or untrusted input (seed, signing, request decoding, review, matching, response encoding) gets a fresh JavaScript VM, released afterwards. Only two public operations over the device's own authenticated public index (address pages and pairing export) reuse a warm VM, which never receives secrets or external data and is dropped whenever the app is suspended (background, App Lock, screen capture). While wallets are on screen, BitTool Signer prepares each wallet's opening Connect QR (Bitcoin account xpub) in the background so the page opens complete; this uses the same warm operation on the same public index, is kept in memory only, and is discarded on suspend or when wallet data changes. An animated QR scan uses its own VM for incremental frame collection, discarded when the scan ends.
- BIP39 seed derivation (PBKDF2-HMAC-SHA512, 2,048 rounds, NFKD) runs natively with CommonCrypto. The engine receives the 64-byte seed instead of the phrase for derivation and signing, and the native buffers are wiped with `memset_s` after use. Published BIP39 vectors and engine parity are tested.
- Both `crypto.getRandomValues` and `Math.random` are backed by native `SecRandomCopyBytes`. The latter supports dependencies that generate internal identifiers while importing; it does not use JavaScript's default pseudorandom generator.
- Requests are JSON arguments to a fixed dispatch function; request strings are never interpolated into evaluated JavaScript.
- Operation names and request sizes are bounded. QR, CBOR, transaction, path, and integer validation is performed by the engine before signing.
- The production bridge loads the app's bundled engine. Custom source-file injection exists only in `DEBUG` builds for isolation tests and is absent from Release builds.
- Dependencies are pinned in the npm lockfile and bundled before an Xcode build. No engine update or dependency download occurs at runtime.

A fresh context reduces the lifetime of secrets but is not a proof of memory erasure. Swift strings, JavaScript strings, garbage collectors, and library internals can retain copies. Native temporary KDF buffers are overwritten where feasible, but the application cannot guarantee that every copy of a secret has been zeroized. A compromised or jailbroken operating system can observe secrets while they are in use.

## Review before signing

The engine hashes the entire canonical request, independently parses the actual signing bytes and binds returned signatures to that request hash. Native code rechecks request and authorization generations after asynchronous vault authentication, signing and response encoding. Backgrounding or replacing the request invalidates an in-flight operation; a late result cannot be published. Previous partial signatures are preserved while the user authorizes remaining fixed tasks.

An interrupted public match can be retried without a password. Changing the wallet collection or its public key indexes invalidates unfinished plans and intermediate signatures; the reviewed request remains available for an explicit fresh match. A display-name change alone does not change signer identity or invalidate a plan.

Decoding status and risk are separate: fully decoded, partially decoded or opaque; normal, warning or high risk. Structurally valid, signable operations with incomplete semantics require explicit consent for that request. There is no persistent blind-signing setting. Malformed bytes, conflicting signer/network metadata, unsupported spend rules and unverified required context are rejected. A warning never overrides an identity mismatch or changes the bytes being signed.

The scanner reports recognized frames, collection progress, protocol errors, and a retry action in the camera sheet. Camera failures and detected codes without readable text receive separate messages. The current imToken compatibility correction accepts a bounded opaque ETH UR request ID of 1–64 bytes and returns exactly those bytes in the response; the observed request used 36 bytes rather than the previous implementation's fixed 16-byte assumption. This transport correction does not relax transaction parsing, expected-signer checks, or reviewed-hash binding. The original request and user image are not repository fixtures. See [Direct-Signing.md](validation/Direct-Signing.md) for verification status.

Offline inspection cannot establish on-chain token identity, contract behavior, token metadata, current permission membership, blockhash freshness, or current account balances. The app displays these limits and shows raw amounts, recipients, authorities, fees where determinable, and approval risks. Bitcoin change is not inferred from untrusted PSBT labels. Multisig signatures remain partial; they do not establish that all required owners approved or that an on-chain policy has been independently verified. See [Compatibility.md](Compatibility.md) for exact protocol support and exclusions.

### 2026-09-21 review fixes

An internal review of this revision found and fixed the following. Each engine item has a regression test in `engine/test/hardening.test.mjs`; the native items are covered in `BitToolSignerTests/HardeningTests.swift`.

| ID | Fix |
|---|---|
| F1 (critical) | EIP-712 values must match their declared type exactly. Previously a truthy string could be hashed as `bool: true` while the review showed the string. |
| F7, F14 | Ambiguous integer and address spellings are rejected before hashing. The declared `EIP712Domain` order defines the separator, unused types are ignored as wallets do, and a domain value that its declared type omits is rejected. |
| F2 | `eth-signature` returns EIP-155 `v` for legacy transactions and y-parity for typed transactions. |
| F3 | Safe transaction gas refunds (gas token, refund receiver, gas price) are decoded, shown and raise the risk level. |
| F4, F5, F6 | Summaries never pair one transfer's amount with another's destination. Native value attached to contract calls leads the summary on every chain. TRON call value, high fee limits and EVM and Solana fees are shown. |
| F10 | TRON messages that are not valid text are shown as exact bytes and marked opaque, so they need explicit consent. |
| F11, F12 | Solana durable-nonce transactions and transfers of tokens missing from the bundled registry are flagged. |
| F13 | Animated QR frames are collected incrementally in a per-scan context. The result equals batch decoding, and mixed sessions are rejected. |
| F15 | `ur:psbt` requests are accepted and answered with the same UR type. Base64 PSBT files wrapped over several lines decode. |
| F16 | Release builds reject test-only operations, including raw single-key signing. |
| F18 | BIP340 Schnorr signatures use fresh 32-byte auxiliary randomness. |
| F8 | The App Lock background interval uses a clock that counts while the device sleeps. |
| F9 | Vaults authenticate the exact stored header bytes (vault format 2). |
| F17 | Public wallet files are HMAC-authenticated with a Keychain key. |

Bitcoin change is recognised only for outputs whose scripts are re-derived from the signing wallet's own public keys, never from PSBT metadata alone.

## Device and UI boundaries

The app revokes authorization immediately on entering the background, regardless of App Lock's grace period. A native privacy window covers every presented sheet while inactive, backgrounded or captured. A separate lower authentication window preserves existing navigation and modal routes behind App Lock. Unlocking app access does not produce a signing authorization.

Setup retains an unfinished mnemonic and BIP39 passphrase in process memory only. Backgrounding clears passwords and backup-question selections, conceals the full phrase and discards decrypted saved-wallet backups. Restore text and verification choices remain visible after returning. Closing setup or terminating the process discards its draft.

Public unsigned requests, reviews and completed signature responses can remain in memory across suspension. The password and risk acknowledgement cannot. Each new signing task requires its own password. The final signature response does not imply broadcast or confirmation.

Activity is a bounded protected local journal of public signing metadata. An unreadable journal is not overwritten with a new one-entry history. Receipt-storage failures are reported separately without discarding the signature. App Lock, when enabled, protects access to these records with the rest of the UI.

Creation has four steps: configure/generate, back up the full phrase, pass the backup check, and set a wallet password. The backup screen follows a Words | QR Code layout, modelled on Ownbit's backup flow in BitTool Signer's own styling. Every form of the phrase (the word grid, the QR code and the recovery cards) starts concealed and is shown by a single tap on the concealed placeholder; there is no second confirmation alert, because the tap itself is the deliberate act and the placeholder already says to make sure no one can see the screen. Concealed content is absent from the rendered view and accessibility tree, rather than merely blurred. A reveal is refused while the app is not active, while the screen is being captured, and until a screenshot warning has been acknowledged. Leaving those displays, app inactivity, backgrounding, a screen-capture change or a screenshot conceals them again. The words and the QR code are revealed separately, and switching between them conceals the other. The Settings backup and its BIP39 passphrase use the same concealment. “I’ve Written Them Down in Order” is enabled only after the words have been shown once, in the grid or on the recovery cards; showing only the QR code does not count.

The **QR Code** tab shows the phrase itself as a plain-text QR code (the words separated by spaces), for moving the wallet to another device of your own; any wallet that can scan a recovery phrase can read it, and BitTool Signer's import reads it with its exact spelling. It is a complete copy of the secret: the tab says so, a red warning states that anyone who scans or photographs it can take the funds and that no one will ever ask to see it, and the app never offers to save, print or share it. It contains the words only; when the wallet has a BIP39 passphrase the tab says the passphrase is not included. The earlier encrypted-QR format (`BSBK1:`) and its add-only Photos permission are removed.

**Recovery Cards** split the phrase across three cards so that any two restore it. Positions are laid out in rows of three and each card leaves out one word per row, shifting by one position every row, so each card lacks exactly a third of the words and every word appears on two cards. The layout depends only on the word count (never on the words), so cards written at different times, or recreated on another device, always fit together; each card lists the positions it leaves out. One card alone cannot restore the wallet, but it still reveals two thirds of it. With 24 words the 8 missing words leave about 80 bits to guess (88 bits less the 8 checksum bits); with 12 words only 4 words (40 bits) are missing, which is within reach of a determined attacker with GPUs, so for 12- and 15-word phrases (40 and 50 bits) the cards screen warns to guard every card like the full phrase or to use a 24-word phrase. The cards contain no BIP39 passphrase. They have their own tap-to-reveal and conceal on the same events as the grid.

Restore has two steps: enter and validate the phrase, then set a wallet password. Phrases in any of the ten official BIP39 languages are accepted (English, Simplified and Traditional Chinese, Japanese, Korean, Spanish, French, Italian, Czech, Portuguese). The wordlists are bundled byte-for-byte from bitcoin/bips, pinned by SHA-256 and cross-checked against two independent libraries; validation, including the checksum, runs natively. Input is forgiving: any whitespace (including the Japanese ideographic space) and commas separate words, numbering such as “1.” is ignored, Chinese typed without spaces is split into its one-character words, and Latin-script words may be typed without accents or in capitals. The seed is always derived from the canonical words (NFKD, as BIP39 specifies), and the vault stores them in NFC. Exact spellings are matched first in every language; words spelled the same in two lists are the same string and give the same seed. Typed accents are treated as deliberate. When unaccented words form a valid phrase in more than one language (for example an Italian phrase that is also Spanish once accents are added), each reading is a different wallet, so the app asks which language the backup is written in instead of guessing. The multiline `TextEditor` is directly visible and uses the system keyboard, so Apple’s Chinese, Japanese and Korean input methods can be used; autocorrection, autocapitalization and content-type autofill are disabled, and Writing Tools are disabled on iOS 18 and later. CJK input methods may still remember converted words in their own dictionaries; after importing, people can reset the keyboard dictionary in iOS Settings. The app separately rejects third-party keyboard extensions through `AppDelegate`, because ordinary text input does not receive the automatic keyboard restriction of a secure field. See Apple's [custom keyboard guidance](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html). These controls do not prevent screenshots, observation, accessibility access, or system copy/paste. Local validation does not establish ownership, the intended BIP39 passphrase, or on-chain balances. Restore skips the creation-only backup screens. Its password page allows returning to edit the phrase, preserving the draft while clearing wallet passwords; the final action restores an encrypted local vault using the same storage protection as creation. Scanning a QR code that contains the words (in any of the ten languages, such as BitTool Signer's own recovery phrase QR) fills the editor; because a QR code carries the exact spelling, an exact-spelling reading is taken without the language question while the scanned text is unedited. Standard SeedQR scanning is supported for English phrases, as that format defines.

The backup check (creation Step 3) shows every position with its word masked, except four random blanks (five for 18 words or more). The blanks’ words are offered as shuffled chips, never in answer order, and must be placed back in order; tapping a filled blank removes its word. Correctness is evaluated for the whole check only, and is not encoded in chip labels or accessibility identifiers. A wrong attempt clears the placements and keeps the same blanks and chip order. Backgrounding and screenshots also clear placements. The chips are real phrase words, so this screen is not safe to photograph merely because most words are masked.

The device-passcode explanation card is removed from both setup routes. This is a presentation change only: encrypted-vault creation, including a restored vault, still requires the same `WhenPasscodeSetThisDeviceOnly` Keychain protection and has no weaker fallback.

The app observes `UIApplication.userDidTakeScreenshotNotification` on active recovery screens. It conceals any revealed full-phrase backup (words, QR code or recovery cards), and nothing can be shown again until the warning is acknowledged. On the directly visible restore editor and verification screen, it presents a warning; verification selections are also cleared, but this does not turn either screen into a concealed display. The notification occurs **after** the screenshot; BitTool Signer cannot prevent or delete the captured image. The warning asks users to remove it, including Recently Deleted and synced copies, and keep a written offline backup. Clearing answers or hiding content afterward cannot remove words or selections already captured.

Screen recording or mirroring can trigger a lock and privacy cover. A background cover reduces exposure in the application switcher. These controls do not prevent every screenshot, external camera, accessibility capture, or observation before the screen is covered. iOS has no general public API that reliably prohibits user screenshots of arbitrary application content. See [Apple's screenshot notification API](https://developer.apple.com/documentation/uikit/uiapplication/userdidtakescreenshotnotification).

The app has no network monitor, reachability probe, network status indicator or standing connectivity warning. Network isolation advice appears in onboarding. No HTTP/RPC client, remote content, analytics or network-capable JavaScript bridge is exposed. Static token metadata/icons are bundled and selected by chain plus address, never by symbol alone. A known registry entry does not verify current on-chain behavior. The Terms of Use and Privacy Policy ship as bundled text and are read inside the app, so nothing opens a browser. The only exit to another app is the camera-permission button, which opens iOS Settings.

For the 2026-09-21 bundle, an in-memory rebuild produced the same SHA-256 and confirmed that ethers fetch/provider modules contribute no code to the delivered output. The manifest's input list includes source files inspected during bundling; it does not mean those files survived tree-shaking. The JavaScriptCore host supplies native entropy without network interfaces. This is a property of the audited implementation, not an OS-level networking prohibition.

The iOS wireless-data authorization dialog is controlled by the OS. Removing automatic networking APIs addresses the app-controlled startup path; suppression of that dialog must still be verified on affected physical hardware. Denying network access does not prevent local wallet creation, derivation, QR handling, or signing. User-selected Files/share providers may use their own network services; this is separate from BitTool Signer's local signing operations. Other software on the device can still use networking when enabled.

## Validation and release requirements

Automated native tests cover password boundaries, secure entropy bounds, a PBKDF2 vector independently generated with Python, AES round trips and fresh salts, wrong password/device keys, authenticated metadata and ciphertext tampering, excessive KDF parameters, multiple vaults, password rotation, reauthenticated deletion, retry-state persistence, and JavaScriptCore context isolation. A bundled-engine test checks a BIP39 vector and account derivation through the actual native bridge. Engine tests separately verify supported-chain signatures and malformed requests.

Current revision results, bundle hash and limits are recorded in [IMPLEMENTATION_STATUS.md](../IMPLEMENTATION_STATUS.md). Earlier reports in `docs/validation` remain historical evidence and do not establish acceptance of this revision. Tests use public, unfunded vectors and synthetic requests, never user secrets or production transactions.

Before any production distribution or recommendation for significant funds:

- Obtain independent review of vault storage, native lifecycle handling, JS dependencies, transaction parsing, multisig policy, QR transport, and the complete application.
- Run signed-device tests on the oldest and newest supported iOS versions, including Keychain behavior, passcode removal, app reinstall, locked-device storage access, backup/restore exclusion, power interruption during password changes, and page retention with secret concealment after backgrounding.
- Verify both light and dark mode, VoiceOver/Dynamic Type, camera permission transitions, recording/mirroring, app-switcher covers, the 120-second background App Lock boundary, and custom keyboard restrictions.
- Validate end-to-end requests and responses against specific released versions of each supported hot wallet on test networks or with intentionally disposable keys and small amounts.
- Review dependency advisories and licenses, retain lockfiles and build hashes, reproduce the JS bundle, inspect the Release archive for test fixtures or debug entry points, and complete App Store privacy/signing requirements.

Passing protocol tests or building successfully does not replace this work or prove that a third-party wallet integration is certified.
